# dukou（渡口）

> 给国内机器开一条到海外的出网通道，装好 AI 命令行工具，配好分流，出问题能自己说清断在哪一层。

两条路，任选一条：

- **桌面版**：双击打开，填三个框，点开始。适合不想碰命令行的人。
- **命令行版**：`dukou server` + `dukou client`。适合批量部署或写脚本。

两者共用同一份内核（`internal/`），行为一致，不是两套实现。

## 桌面版（推荐）

```
┌────────────────────────────────────┐
│  渡口 · 一键部署                     │
│                                    │
│  服务器 IP   [47.251.92.212] [22]  │
│  SSH 账号    [root]                │
│  SSH 密码    [********]            │
│  本机密码    [********]            │
│                                    │
│  ☑ 同时安装 Codex                  │
│                                    │
│            [ 开始部署 ]             │
└────────────────────────────────────┘
```

点开始之后是四条进度：

| 步骤 | 它在做什么 | 失败时说明什么 |
|---|---|---|
| 1 · 测试连接 | SSH 登录、读系统信息 | 密码错 / 端口不通 / 不是 root |
| 2 · 配置服务器 | 装 gost、起服务、放行端口 | 云安全组没开 / 端口被占 |
| 3 · 配置本机代理 | 装客户端、设系统代理与环境变量 | 链路不通（会给出排查命令） |
| 4 · 安装 Codex | 检查 Node → 装 Codex → 验证 | Node 版本过低 / npm 网络不通 |

四条全绿后，界面显示服务器地址、代理账密、**实测出口 IP** —— 出口 IP 是实测的，不是猜的。

### 安装

从 [Actions](https://github.com/yijiuba/dukou/actions) 最新一次构建里下载：

- Linux：`dukou-desktop-linux-amd64`
- Windows：`dukou-desktop-windows-amd64.exe`

```bash
chmod +x dukou-desktop-linux-amd64 && ./dukou-desktop-linux-amd64
```

### 三件它做不到的事

把边界说清楚，比含糊承诺有用：

1. **云安全组要你手动放行一个端口。** 安全组在云控制台，不在机器里，程序改不了。检测到没放行时，它会停在第 2 步并告诉你具体点哪里、填什么。
2. **AI 工具的登录要你本人点。** Codex 首次运行会弹浏览器做 OAuth，这一步只能人来。
3. **它不替你保管密码。** 代理密码随机生成后直接写进两端配置，界面显示一次，抄走后自己存好。

## 命令行版

```bash
# 第一步，在海外服务器上开出口
sudo dukou server --port 8443

# 第二步，在国内机器上接通道
sudo dukou client --server <服务器IP> --port 8443 --profile codex

# 第三步，任何时候觉得不对劲
dukou doctor
```

| 命令 | 作用 |
|---|---|
| `dukou server` | 部署服务端，只对外暴露一个 TLS 端口 |
| `dukou client` | 起本地中转，配置分流，安装目标 CLI |
| `dukou doctor` | 七层诊断：环境 → 端口 → 连通 → 鉴权 → 转发 → 分流 → 性能 |
| `dukou rotate-password` | 生成随机密码并同步两端 |
| `dukou uninstall` | 按 manifest 清单精确回滚，不留残渣 |

## 它解决的不是"没有代理"，而是"配了也不通"

代理本身从来不是难点。难点是每一步都可能以「看起来正常」的方式失败：

- 代理要鉴权，`curl -x` 漏带密码返回 407，而 `-s` 会把它吞成空白，看起来像断网
- 明文 `CONNECT` 请求头带着域名过境，被中间设备直接 RST —— 表现为"有的网站能开、有的永远不行"
- 系统代理是全局的，访问国内站点也绕一圈出国，内网域名直接 503（`apt` 装不上就是这个原因）
- 浏览器能通但命令行不通，因为图形界面的系统代理和终端的 `HTTP_PROXY` 是两套东西
- 跨境丢包 12%、RTT 155ms，升带宽毫无用处；换 BBR 后吞吐从 23KB/s 到 1.65MB/s

这些坑的共同点：**现象指向的位置和真正的原因不在同一层**。对应的两个核心设计：

1. **服务端只开 `http+tls`，客户端用 `-F tls://` 对接。** 跨境链路上域名不可见，绕开协议层识别。
2. **每一步都自检。** 装完立刻验证，验不过当场停，而不是十分钟后由用户偶然发现。

```
Firefox ──系统代理──┐
Codex/终端 ──环境变量──┴→ 127.0.0.1:7890 ──TLS 8443──→ 海外服务器 → 目标服务
                          （NO_PROXY 里的国内域名直连）
```

## 开发

需要 Go 1.22+。核心与命令行零第三方依赖；桌面版引入 Wails 与 `x/crypto/ssh`。

```bash
go build ./...                              # 核心 + CLI
go test ./... -race                         # 单元测试
go build -tags gui ./desktop                # 桌面版
```

桌面包带 `gui` 构建标签，默认的 `go vet ./...` 与 `go test ./...` 不碰它 —— 否则每个
CI 单元测试都得先装 GTK 头文件。Linux 上编桌面版需要：

```bash
sudo apt install -y libgtk-3-dev libwebkit2gtk-4.1-dev
```

### 测试分四层

| 层 | 内容 | 在哪跑 |
|---|---|---|
| L0 单元测试 | 发行版归并、架构映射、单元渲染、文件写入编码 | 本地 + CI |
| L1 容器矩阵 | Ubuntu / Debian / Alma / Alpine / Arch 里真跑二进制 | GitHub Actions |
| L2 真机集成 | 按量付费临时云服务器，验证真实 systemd 与防火墙 | 手动 |
| L3 生产灰度 | 真实环境，含手工配置的收编 | 手动 |

L1 里 Alpine 那条最关键：它用 musl libc，glibc 编译的程序在那里根本起不来。这条能过，
就证明"静态二进制兜底"成立 —— 任何 Linux 至少有 tar.gz 这条路可走。

一条约定：任何层发现的 bug，先在 L0 补一条对应用例再修。

## 适用边界

这个工具做的是**部署 AI 工具的运行网络环境**，不提供、也不代理任何模型服务本身：

- 你自备海外服务器，自备模型账号或 API Key
- 凭证只存在你自己的机器上，工具不上传、不代管
- 不承诺任何服务在特定地区的可用性，这取决于你的服务器与目标服务
- 请在所在地法律法规允许的范围内使用

## 已知取舍

- **SSH 主机密钥不校验。** 首次连接时用户还没机会确认指纹，强制校验会把所有人挡在门外。代价是理论上可能被中间人冒充。
- **代理密码会短暂出现在界面上。** 需要让用户抄走一次。
- **只支持 systemd。** 容器、OpenWrt 不在范围内。
- **`nftables` 只提示不改。** 生成规则容易，改错防火墙把人锁在门外更容易。
