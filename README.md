# dukou（渡口）

> 国内机器一键接入海外大模型 —— 开一条出网通道，装好 CLI，配好分流，出问题能自诊断。

`dukou` 是一个单文件命令行工具。它把「在海外服务器上开代理、在国内机器上接通道、配好浏览器与包管理器的分流、装上 Codex 这类大模型命令行工具」这一整套手工流程，收敛成两条命令。

## 它解决的不是"没有代理"，而是"配了也不通"

代理本身从来不是难点，难点是**每一步都可能以「看起来正常」的方式失败**：

- 代理要求鉴权，`curl -x` 没带密码返回 407，而 `-s` 会把它吞成空白，看起来像断网
- 系统代理是全局的，访问国内站点也绕一圈出国，内网域名直接 503
- 明文 `CONNECT` 请求头带着域名过境，被中间设备直接 RST，表现为"有的网站能开、有的永远不行"
- 命令行能通但图形界面不通，因为从 Dock 启动的程序不读 `profile.d`
- 跨境丢包 10%，升带宽毫无用处，换拥塞算法后吞吐提升几十倍

这些坑的共同点是：**现象指向的位置和真正的原因往往不在同一层**。`dukou doctor` 把排查经验编码成五层测试链，任何一层失败就直接告诉你断点在哪、该敲什么命令。

## 前置条件

- 一台能正常访问目标服务的**海外服务器**（阿里云、腾讯云、AWS 等均可），有公网 IP
- 国内那台机器需要有 root 或 sudo
- 两端都支持 Linux（Debian/Ubuntu、RHEL/CentOS/Rocky/Alma、openSUSE、Arch、Alpine）

## 快速开始

**第一步，在海外服务器上开出口：**

```bash
curl -fsSL https://raw.githubusercontent.com/yijiuba/dukou/main/scripts/install.sh | sudo bash
sudo dukou server --port 8443
```

**第二步，在国内机器上接通道并装 CLI：**

```bash
sudo dukou client --server <服务器IP> --port 8443 --profile codex
```

**第三步，任何时候觉得不对劲：**

```bash
dukou doctor
```

## 命令

| 命令 | 作用 |
|---|---|
| `dukou server` | 在出口服务器上部署服务端，只对外暴露一个 TLS 端口 |
| `dukou client` | 在国内机器上起本地中转，配置分流，安装目标 CLI |
| `dukou doctor` | 五层诊断：环境 → 连通 → 鉴权 → 转发 → 性能 |
| `dukou rotate-password` | 生成随机密码并同步两端 |
| `dukou selfcheck` | 快速自检服务状态、拥塞算法、分流、CLI |
| `dukou uninstall` | 按 manifest 清单精确回滚，不留残渣 |

全局开关：

| 开关 | 作用 |
|---|---|
| `--dry-run` | 只打印执行计划，不改动系统 |
| `--takeover` | 显式授权接管被占用的端口 |
| `--port N` | 指定端口，避开冲突 |

## 三条设计原则

**单一配置源。** 服务器地址、账密、端口只写在 `/etc/dukou.conf` 一处，其余组件全部引用变量。两端密码差一个字符导致的 407 曾经是最难查的故障。

**每一步都有验证门。** 装完就验，验不过就停，并打印出失败的那一层。不做"全跑完再一起排错"。

**所有改动可回滚。** 工具写过的每个文件、建过的每个服务、加过的每条防火墙规则都记录在 `/var/lib/dukou/manifest.json`，`uninstall` 按清单逆序还原，不靠猜测。

## 适用边界

这个工具做的是**部署 AI 工具的运行网络环境**，它不提供、也不代理任何模型服务本身：

- 你自备海外服务器，自备模型账号或 API Key
- 凭证只存在你自己的机器上，工具不上传、不代管
- 不承诺任何服务在特定地区的可用性，可用性取决于你的服务器与目标服务
- 请在所在地法律法规允许的范围内使用

| 层 | 内容 |
|---|---|

一条约定：任何层发现的 bug，先在 L0 补一条对应测试用例再修复。
